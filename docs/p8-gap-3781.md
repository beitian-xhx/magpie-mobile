### 4.2 锚点逐字核对结果

对 manifest.json 全部 34 个 replacement 锚点在 3781 文件中做逐字校验：**33 个命中、1 个失效**。

### 4.3 其余升级约束核对

- `manifest.json` 的 `checks` 仅含 go.mod sha256：**go.mod 在范围内零变更** → 校验通过，无需改。
- 17 个 overlay 文件全部为加性新文件：上游范围内**新增 0 个 `mobile*` 文件、未创建 `internal/mobilepolicy` 目录** → 无命名碰撞。
- lan.go 补丁插入代码调用的 `access.Authenticate` 在 3781 存在（internal/access/access.go:741）→ 重锚后编译语义成立。

- 风险点沿用 P5 §5：8 文件重钉 sha256 后需全量契约/JVM/Go 测试；新核心二进制 SHA-256 变化改变 APK 哈希；Bun 运行时与插件兼容需在新核心下重验（fetch-assets.sh 钉死版本）。

**结论：升级是低摩擦的——1 个锚点重锚 + 8 文件重哈希，无结构冲突。**

## 5 建议落地顺序

1. **A5 先行（S）**：`UsageClient` 对 `speeds`/`speed_min` 的解析为纯增量、零风险，可与 0.1.34 结构线并行（解析容错，核心未升级时字段不出现）。
2. **核心升级 3781（P9 线，一次性）**：收益最大的是 C类 行为修复（网关路由/掩码/限额/代理），A类端点全部依赖它才存在。执行 = 既有三件套（CI ref + CORE_VERSION + manifest 8 文件重哈希）+ lan.go 重锚，走已激活的升级发版技能流程。
3. **升级后按 A4 → A1 → A2 → A3 顺序落地**：A4/A3 为 S 级单客户端方法；A1/A2 为 M 级（白名单 3+1 条精确路径 + 面板控件 + 单测）。
4. **B类维持不落地**；若用户点名 Bark 推送或命名代理等单项，另行立项按「移动原生实现 or 白名单放行」二选一重审，不批量开放 settings 写面。
5. 移动契约守护项：升级后首轮回归必须含 `/api/mobile/capabilities` 契约、provider 严格字段白名单（mobile_providers.go 的 unknown-field 拒绝路径）、`GET /api/providers` 脱敏解析三组测试。
